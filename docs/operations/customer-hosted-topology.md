# Customer-Hosted Deployment Topology

Customer-hosted LMS uses the same core application/domain codebase as SaaS, with provider adapters and environment-specific infrastructure.

## Baseline topology

~~~mermaid
flowchart TB
    U[Customer/Vendor Admin Browser] --> RP[Reverse Proxy / TLS]
    RP --> LMS[LMS Application / Workers]
    LMS --> PG[(PostgreSQL)]
    LMS --> AR[(Artifact Repository / MinIO or approved storage)]
    LMS --> SG[Signing Gateway / Protected Provider]
    LMS --> SMTP[SMTP / Notification Relay]
    LMS --> OBS[Logs / Metrics Export]
    EDGE[Edge Devices] <--> RP
~~~

## Required components

- TLS termination/reverse proxy or equivalent
- persistent PostgreSQL
- persistent artifact repository
- LMS application + durable background workers/scheduler
- protected signing provider integration
- secrets/configuration mechanism
- backup destination
- monitoring/log export
- time synchronization
- email relay if notifications enabled

## Network/port principle

Only required interfaces are exposed. PostgreSQL/artifact/signing internal endpoints should not be publicly reachable. Edge devices connect to the approved LMS/reverse-proxy endpoint. Exact port/firewall matrix is generated by deployment packaging and security profile.

## Identity

Human authentication may integrate with customer IdP after ADR-008 is resolved. Device authentication remains cryptographic and independent of customer human SSO.

## Storage

PostgreSQL stores transactional metadata; large binaries use MinIO/approved local repository. Backup/restore covers both. Raw signing private keys are outside ordinary storage/backup.

## Installation

Initial deployment package validates OS/runtime prerequisites, DB connectivity/schema, artifact storage, signing provider, time and required certificates before marking LMS ready.

## Upgrade

Customer-hosted LMS self-update is manual initially:
1. validate supported source version
2. obtain signed LMS package
3. take verified backup
4. verify package signature
5. run automated migration/update
6. health-check API/workers/dependencies
7. validate safe device check-in/signing
8. record upgrade evidence

## Failure/recovery

Customer-hosted recovery follows backup/DR runbooks. Unsafe DB downgrade is prohibited; release declares rollback versus forward-fix compatibility.

## HA

HA is an enterprise option rather than mandatory Phase 1. Exact app/DB/storage/load-balancer topology and RTO/RPO are deployment-tier decisions; business/domain behavior remains unchanged.

## Security

Customer-hosted does not mean trusted-by-default. Tenant checks, signing separation, audit, secret handling, package verification and least-privilege requirements still apply.
